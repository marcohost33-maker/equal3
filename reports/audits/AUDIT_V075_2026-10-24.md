## 1. Decision and scope

The previous response correctly separated a verified local research candidate (v0.7.4, 113 tests) from a production release. However it left the most important architectural blockers open: non-atomic DB/witness, lack of independent monotonic trust, potential raw-writer bypass and plaintext persistence. Green unit tests and 87% code coverage **do not** address those architectural trust boundaries.

This development provides a *testable* two-phase protocol but **does not deploy** an independent anchor. `MemoryCASAnchor` lives in the same process; it has no durable monotonic journal and its test-only reviewer credential is accessible in the test runtime. This is a research model, not P0 closure.

## 2. New implemented work

1. `anchor_protocol.py`: `Position=(store_id,version,digest)`, `Intent=(store_id,base_version,base_digest,next_version,next_digest,request_id,proposal_hash)`, thread-serialized `MemoryCASAnchor` with monotonic CAS and a single pending slot, `CoordinatedStore` that creates pending intent **before** SQLite commit and stops on unknown outcomes.
2. `state_store.inspect_request(rid)`: all historical V2 receipt-chain validation, current state and the exact request receipt in one SQLite pinned read transaction. Checks proposal hash, digest and exact next version before a simulated finalize.
3. Explicit verdicts: `MATCH`, `NOT_COMMITTED_HOLD`, `COMMITTED_PENDING_HOLD`, `ROLLBACK_HOLD`, `DIVERGENCE_HOLD`, `INVALID_DB_HOLD`, `CONFLICT_HOLD`, etc. **No automated recovery** from an unknown commit.
4. Reviewer-token HMAC is bound to decision, request, store, current/new digest, versions and entire proposal fingerprint. Test-only backend rejects unauthorized or previously used token; **production requires independent reviewer authentication** and independently verifiable DB attestation.
5. Read fix: compare the **actual returned snapshot** to one authority status; do not diagnose at T1 then read unverified data at T2. Concurrent uncooperative actors are still explicitly outside the tested runtime isolation.

## 3. Formal assumptions and invariants

- Assumptions: one trusted, cooperating writer; trustworthy Python process; SQLite local POSIX store and master key; volatile anchor simulator. Separate operating-system identities and authenticated remote endpoints are **not** implemented.
- Invariant I1: `Pending == None` for MATCH; `db_version = anchor_version` AND `db_digest = anchor_digest` AND V2 receipt history valid.
- Invariant I2: remote Prepare may begin only from exact anchored `(store_id,version,digest)`; next version is `old_version+1`.
- Invariant I3: `CommitUnknown` or any fault after prepare leaves a HOLD; only approved, freshly validated `COMMITTED_PENDING_HOLD` can finalize, only `NOT_COMMITTED_HOLD` can abort.
- Invariant I4: anchor API cannot decrement its committed version and one pending intent blocks another writer.
- Invariant I5: a snapshot read must refer to the exact DB version and digest it returns, not an earlier version from an unrelated audit.
- Adversarial limit: Attacker controls raw SQLite writer and key -> can bypass trusted coordinator. Attacker rolls back SQLite **and** test anchor process -> state can appear old and valid; the *independent fault domain* is absent.

Do **not** skip authenticity checks solely to improve latency.

## 6. P0 risks, falsification and source authentication

The biggest remaining architectural flaw is authentication of the **writer's claim** at the authority. In this reference the simulated backend trusts the coordinator to have checked the DB; a compromised coordinator can lie about the SQLite outcome. Production requires remote-side authorization and verifiable evidence, with independent anchor provenance, an isolated writer OS identity, key separation and a stable protocol with expected crash semantics.

SQLite transaction durability is controlled by journal mode, synchronous policy, filesystem/hardware contract and actual VFS behavior. SIGKILL hooks from earlier versions do not simulate partial sector writes or reordering. A serious P0 test program must use SQLite crash-test VFS methodology, distinct injection classes and an independent evaluation run.
